Beyond the HTML pages, this project publishes the same content in forms that tools can read
directly: a site index, the full corpus as one file, per-page raw Markdown, and generated social
images. All of it is derived from the same `source`, so it never goes stale.

## `/llms.txt`

```ts title="src/app/llms.txt/route.ts"
import { source } from '@/lib/source';
import { llms } from 'fumadocs-core/source';

export const revalidate = false;

export function GET() {
  return new Response(llms(source).index());
}
```

An outline of the whole site, following the [llmstxt.org](https://llmstxt.org) convention: a
Markdown list of every page with its title, URL, and description, nested to match the sidebar.
Separators become bold headings. It is the cheap way for an AI tool to learn what exists before
fetching anything.

```bash
curl -s http://localhost:3000/llms.txt
```

## `/llms-full.txt`

```ts title="src/app/llms-full.txt/route.ts"
export const revalidate = false;

export async function GET() {
  const scan = source.getPages().map(getLLMText);
  const scanned = await Promise.all(scan);

  return new Response(scanned.join('\n\n'));
}
```

Every page's Markdown, concatenated. One request gets an agent the entire documentation set.

<Callout type="warn">
  The response size grows linearly with the site. Since `revalidate = false` it is generated once at
  build time rather than per request, so the cost is build time and bundle size, not latency. On a
  large site it is worth measuring.
</Callout>

## `/llms.mdx/docs/*/content.md`

```ts title="src/app/llms.mdx/docs/[[...slug]]/route.ts"
export const revalidate = false;

export async function GET(_req: Request, { params }: RouteContext<'/llms.mdx/docs/[[...slug]]'>) {
  const { slug } = await params;
  const page = source.getPage(slug?.slice(0, -1));
  if (!page) notFound();

  return new Response(await getLLMText(page), {
    headers: {
      'Content-Type': 'text/markdown',
    },
  });
}
```

One page as raw Markdown. Note `slug?.slice(0, -1)` — the trailing `content.md` is a synthetic
segment added by `getPageMarkdownUrl()` and must be removed before the lookup. See
[Source API](/docs/development/source-api).

This route is what powers the **Copy Markdown** button and the **View as Markdown** option in the
popover at the top of every docs page.

## Content negotiation

`proxy.ts` makes the raw Markdown reachable at friendly URLs — or it would, if Next.js were loading
it.

<Callout type="error" title="This is currently inactive">
  `proxy.ts` sits at the repository root, but this project keeps its app directory at `src/app`, and
  Next.js resolves the proxy file relative to that. It scans `src/` and accepts the file only at
  `/` or `/src` **relative to the app directory's parent** — which here means `src/proxy.ts`. The
  root copy is never loaded, so neither negotiation rule runs today.

  Verified against 16.2.12: `/docs/writing/frontmatter.md` returns a 404 HTML page, and an
  `Accept: text/markdown` request returns HTML with no `Vary: Accept`. Moving the file to
  `src/proxy.ts` makes both return `200 text/markdown` immediately.

  ```bash
  git mv proxy.ts src/proxy.ts
  ```

  Nothing else changes — the file already imports through the `@/lib/shared` alias, which resolves
  from either location. The rest of this section describes the behavior you get once it is moved.
</Callout>

```ts title="proxy.ts"
import { NextRequest, NextResponse } from 'next/server';
import { isMarkdownPreferred, rewritePath } from 'fumadocs-core/negotiation';
import { docsContentRoute, docsRoute } from '@/lib/shared';

const { rewrite: rewriteDocs } = rewritePath(
  `${docsRoute}{/*path}`,
  `${docsContentRoute}{/*path}/content.md`,
);
const { rewrite: rewriteSuffix } = rewritePath(
  `${docsRoute}{/*path}.md`,
  `${docsContentRoute}{/*path}/content.md`,
);

export default function proxy(request: NextRequest) {
  const result = rewriteSuffix(request.nextUrl.pathname);
  if (result) {
    return NextResponse.rewrite(new URL(result, request.nextUrl));
  }

  if (isMarkdownPreferred(request)) {
    const result = rewriteDocs(request.nextUrl.pathname);

    if (result) {
      return NextResponse.rewrite(new URL(result, request.nextUrl), {
        headers: { Vary: 'Accept' },
      });
    }
  }

  return NextResponse.next();
}
```

<Callout title="proxy.ts is middleware">
  Next.js 16 renamed `middleware.ts` to `proxy.ts` — same default export, same semantics. It must
  sit beside the app directory: `proxy.ts` at the root for a root-level `app/`, or `src/proxy.ts`
  when the app lives in `src/app` (this project). Having both a `middleware` and a `proxy` file is a
  build error, and `middleware.ts` now warns as deprecated.
</Callout>

Two rules, in order:

1. **`.md` suffix, unconditional.** `/docs/writing/frontmatter.md` rewrites to the Markdown route.
   An explicit suffix always wins.
2. **`Accept` header, conditional.** If the request prefers Markdown over HTML, `/docs/writing/frontmatter`
   serves Markdown instead of the page, with `Vary: Accept` so caches keep the two representations
   apart.

Anything else falls through untouched.

```bash
curl -s http://localhost:3000/docs/writing/frontmatter.md | head
curl -s -H 'Accept: text/markdown' http://localhost:3000/docs/writing/frontmatter | head
curl -s http://localhost:3000/docs/writing/frontmatter | head   # HTML
```

Until the file is moved to `src/proxy.ts`, the first two return HTML — a 404 page and the ordinary
docs page respectively.

Both patterns are built from `docsRoute` and `docsContentRoute` in `src/lib/shared.ts`, so renaming
a route there keeps the proxy in sync automatically.

Note that the `/llms.mdx/docs/*/content.md` route works regardless — it is a real route, not a
rewrite. Only the friendly URLs depend on the proxy.

## OG images

```tsx title="src/app/og/docs/[...slug]/route.tsx"
export const revalidate = false;

export async function GET(_req: Request, { params }: RouteContext<'/og/docs/[...slug]'>) {
  const { slug } = await params;
  const page = source.getPage(slug.slice(0, -1));
  if (!page) notFound();

  return new ImageResponse(
    <DefaultImage title={page.data.title} description={page.data.description} site={appName} />,
    { width: 1200, height: 630 },
  );
}
```

A 1200×630 social preview per page, rendered from the page's own title and description with
`appName` as the site label. Same `slice(0, -1)` convention, this time stripping `image.png`.

The docs page wires it into metadata:

```tsx
openGraph: {
  images: getPageImageUrl(page).url,
}
```

Check one in the browser:

```
http://localhost:3000/og/docs/writing/frontmatter/image.png
```

<Callout type="warn">
  The image renders `appName` from `src/lib/shared.ts`, which is still `'My App'`. Every generated
  preview carries that label until it is replaced — see
  [Configuration](/docs/operations/configuration).
</Callout>

To restyle, replace `DefaultImage` with your own JSX. `ImageResponse` supports a limited subset of
CSS — flexbox, absolute positioning, no grid — and custom fonts must be loaded and passed
explicitly.

## Verifying the whole surface

```bash
curl -s http://localhost:3000/llms.txt
curl -s http://localhost:3000/llms-full.txt | head -40
curl -s http://localhost:3000/llms.mdx/docs/writing/frontmatter/content.md
curl -s http://localhost:3000/docs/writing/frontmatter.md
curl -sI -H 'Accept: text/markdown' http://localhost:3000/docs/writing/frontmatter
```

A new page should appear in all of them without any additional wiring. If one is missing, the page
is not in the source — check its frontmatter first.
