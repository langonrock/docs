When langonrock became a database, the engine under the read model was replaced. The previous one
compiled authoritative Markdown folders into snapshots; this one commits documents with atomic
batches, history and restore. This page compares the two on the same machine, the same seeded
corpus and the same runtime. Neither side is direct folder access, and neither is a vector database.

The read model itself is measured in [benchmarks](/docs/architecture/benchmarks). Here the question
is narrower: what owning the documents cost, and what it bought.

## Status

**Performance acceptance is open.** Neither run meets the rule below: the formal one is unresolved,
and the shorter one on the shipping runtime fails four rows.

| Runtime    | Pairs per size | Rows | Pass | Inconclusive | Fail |
| ---------- | -------------: | ---: | ---: | -----------: | ---: |
| Bun 1.3.12 |             30 |  114 |  109 |            5 |    0 |
| Bun 1.4.2  |             10 |  114 |  105 |            5 |    4 |

The thirty-pair run on Bun 1.3.12 is the formal comparison. Every point estimate in it fits its
budget, but five confidence intervals cross a limit, which leaves the result unresolved rather than
passed.

The released binaries run on Bun 1.4.2, and there the shorter capture fails four rows, all of them
opening a tenant: 34 to 68 percent slower than the old engine at 500 and 5,000 concepts. Both
engines open faster on 1.4.2 than on 1.3.12, but the old one gained more.

Linux and Windows execution has not been verified either. Every number on this page comes from one
Apple M1 Pro with 32 GiB of memory, running macOS.

## The rule

The baseline is commit `0021f08`, extracted into a temporary directory and run by the same
TypeScript harness as the new engine. The corpus has 500, 5,000 or 20,000 concepts in bundles of
500, generated from seed 7. Each pair alternates which engine runs first, and import, open, reads,
edits and a five-tenant memory case each run in a fresh process. Filesystem caches are not cleared,
so these are fresh-process measurements, not cold-disk ones. Warm reads get ten warmup calls and
100 timed ones. Each edit appends a unique marker, commits it, and checks it comes back through
search and `get`.

| Requirement                                                            | Limit                                                           |
| ---------------------------------------------------------------------- | --------------------------------------------------------------- |
| Search, get, section, slice and find                                   | At most 5% regression, at both p50 and p95                      |
| Import, open, first search, edit-to-search and process initialization  | At most 10% regression, at both p50 and p95                     |
| Peak and steady memory                                                 | At most 10% regression                                          |
| Manifest and retrieval                                                 | Exact manifests and checked outputs, unchanged retrieval scores |
| Disk                                                                   | Reported, with no agreed percentage cap                         |
| New database operations                                                | Reported as absolute costs, with nothing to compare against     |

Each latency row gets a seeded paired-bootstrap 95% interval on the ratio of the two engines. A row
passes only when the interval's upper bound fits the limit and fails when its lower bound exceeds
it. Anything in between is inconclusive and earns twenty more pairs; if it stays inconclusive, the
gate stays unresolved. Outliers stay in the data, and a gain in one metric never offsets a failure
in another.

## Manifest and retrieval

Both engines produce exactly equal manifests, whole and per bundle, and equal outputs for every
checked `get`, section, slice, `find` and search, and every edit becomes visible on both. On the
five fixed topic queries of this harness both score 0.8 hit rate and 0.8 mean reciprocal rank at
every size. That is unchanged, not a claim of good retrieval; the [retrieval
benchmarks](/docs/architecture/benchmarks) measure that.

| Concepts | Manifest characters, both sides | Estimated tokens, both sides | Growth |
| -------: | ------------------------------: | ---------------------------: | -----: |
|      500 |                          82,198 |                       20,550 |     0% |
|    5,000 |                         823,408 |                      205,852 |     0% |
|   20,000 |                       3,343,691 |                      835,923 |     0% |

The token estimates are characters divided by four, rounded up. The equality is the stronger
check: the bytes an agent receives did not change.

## What the new operations cost

These have no equivalent in the old engine, so there is nothing to compare them against. Median
milliseconds, ten repetitions per size, on Bun 1.3.12:

| Operation                                       |   500 | 5,000 |  20,000 |
| ----------------------------------------------- | ----: | ----: | ------: |
| Create 25 documents in one batch                |  35.6 |  93.8 |   277.9 |
| Replace 25 documents in one batch               |  13.7 |  39.9 |   132.4 |
| First history page, five revisions              |  1.14 |  1.14 |    1.06 |
| Next history page, five revisions               |  1.08 |  1.36 |    0.93 |
| Restore                                         |  16.6 |  71.4 |   258.2 |
| Reopen and `get` after an interrupted write     |   3.5 |   9.8 |    27.0 |
| Verify retained data and collect, keep ten      |  73.6 | 531.2 | 1,995.6 |
| Winning writer, publication after preparation   |  12.2 |  14.9 |    26.8 |
| Conflicting writer, rejection after preparation |  18.5 |  18.7 |    30.0 |

A commit's cost grows with the tenant, because every commit writes a complete snapshot and source
archive: 25 new documents take 36 ms at 500 concepts and 278 at 20,000. History does not grow,
since a page reads revision records and nothing else.

**Contention.** Two writers prepare changes to the same document against the same revision while a
third process holds a reader with its search index built. Every run checks that exactly one writer
commits, the other is refused, and the reader keeps seeing the content it pinned. At 20,000
concepts the three processes held 1.10 GB together at the barrier, and each writer peaked at about
0.38 GB. Two writers and a reader are a correctness test, not a sustained load test.

**Recovery.** A writer is killed after staging its new `HEAD` and before replacing the committed
one. A fresh process reopens the tenant, reads a concept, confirms the last acknowledged revision is
the one it sees, and fully verifies all ten retained revisions. Killing a process is not losing
power, and nothing here claims behavior after a power failure.

## What it costs on disk

The same ten single-document edits on each side, then ten versions retained, counting snapshots,
source archives, revision records, import state, staging and the original folder:

| Concepts | Before, total allocated | After, total allocated | Change |
| -------: | ----------------------: | ---------------------: | -----: |
|      500 |                 7.66 MB |               12.96 MB | +69.3% |
|    5,000 |                76.40 MB |              129.05 MB | +68.9% |
|   20,000 |               306.72 MB |              518.95 MB | +69.2% |

That is the largest regression on this page, and it is a cost of what the engine keeps. Native
history preserves complete sources, frontmatter and navigation files included, where the old
engine kept compiled snapshots, and the new engine compresses at level 1. Counting the store alone,
without the original folder, allocated bytes at 20,000 concepts rise from 222.0 MB to 434.2 MB,
about 96 percent. [Collection](/docs/database/maintenance) is what bounds it.

## What these numbers do not show

- The corpus is deterministic and synthetic. Other document sizes, bundle layouts, hardware or
  concurrent workloads may behave differently.
- Every capture ran on one machine, macOS on Apple silicon. Linux and Windows have not run these
  workloads.
- The timings measure engine calls and exclude HTTP and MCP transport.
- Crash behavior was established by killing processes, not by cutting power.
- Apart from the one unresolved row above, the process-startup rows are left out, because nothing in
  this comparison explains them.

## Reproduce them

Clone with full history, because the baseline is a commit the runner extracts. Use new output paths
every time; the runners refuse to overwrite existing evidence.

```sh
bun run bench:dbms --output bench/results/dbms/comparison.json
bun bench/dbms/compare.ts bench/results/dbms/comparison.json

bun bench/operations/run.ts --repetitions 10 --output bench/results/dbms/operations.json
bun bench/operations/report.ts bench/results/dbms/operations.json > bench/results/dbms/operations.md
```

The raw captures record the source and native build fingerprints, the machine, the filesystem, the
runtime and every sample, and a capture whose fingerprints changed during the run is refused rather
than reported.
